# Proposal 0002: Local and SSH control routing with ctl

- Status: Implemented
- Created: 2026-09-04

## Summary

`ctl` selects a local or SSH target and routes a product's canonical command
surface to it. Its first control domain is rmux: `ctl rmux` uses the same rmux
commands locally by default and redirects them through OpenSSH when a host is
selected.

## Motivation

Persistent terminal sessions should be reachable on another machine without a
new network listener, application identity system, or second implementation of
the rmux command surface. Local use should remain the simplest path, while
remote use should rely on established OpenSSH configuration and authorization.

## Design

`ctl` is the client-side router. With no host it connects directly to the
current user's local service. With `--host` it starts the system OpenSSH client
and invokes a fixed remote command.

`ctld connect` is a disposable, stateless SSH gateway. It relays one SSH
channel to the fixed owner-only local `rmuxd` endpoint. It owns no session,
terminal, journal, reconnect state, account database, network listener, or
application-level authorization. Closing the gateway ends only that transport
connection.

OpenSSH owns host verification, encryption, user authentication, host aliases,
proxy configuration, and connection multiplexing. `ctl` disables forwarding
and does not accept an arbitrary remote command or daemon endpoint from its
peer.

The rmux protocol remains end-to-end between the rmux client implementation and
`rmuxd`. After an unexpected SSH failure, a replacement channel may resume the
same logical attachment during rmux's bounded reconnect grace. The PTY and
process continue to belong to `rmuxd` throughout.

The desktop app uses the same target-scoped transport. Its workspace may retain
host configuration and references to known sessions, but it is not an
authoritative mirror of a daemon's inventory and does not make remote
connections merely to restore the UI.

## Invariants

1. Local routing is the default and does not start SSH or `ctld`.
2. Remote routing uses the system OpenSSH client and a fixed `ctld connect`
   command.
3. `ctld` is a byte relay and owns no product-domain state.
4. SSH is the remote authentication and authorization boundary.
5. A client cannot choose the remote local socket, service, or command.
6. Transport loss does not terminate an rmux session.
7. Product protocols and command behavior remain shared across local and remote
   transports.
8. The rmux maintenance endpoint is local-only and is never relayed by `ctld`.

## Out of scope

The implemented proposal does not expose arbitrary shell commands, files,
ports, desktop control, background tasks, or remote daemon maintenance. New
control domains, including a future task service, require their own proposal
and explicit remote gateway boundary.

## Unresolved questions

None for the implemented rmux routing boundary. Additional control domains and
Windows host IPC require separate proposals.
